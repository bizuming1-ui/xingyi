# ESP32-S3 集成候选程序（禁止生产使用）

这是实际设备任务的开发候选版，不是可投产的完整交付。按键、NVS 和同步规划由 Arduino loop 独占；Wi-Fi、可信时间及 HTTPS 由独立 FreeRTOS 任务串行运行，使用非等待邮箱交接。启动检查本地配置、证书解析、NVS、互斥锁、邮箱和任务创建；失败时不自动清空数据。存储或状态故障会停止计数及后续网络任务。串口状态不输出 Wi-Fi 信息、设备密钥或生产单编号。

CI 使用空配置编译（该配置运行时必须拒绝启动），不得把其作为生产或真实联网凭据。实际使用需要在本机将 `src/config.example.h` 复制为 `src/config.local.h`，并**通过安全渠道**配置测试项目 Wi-Fi、设备 ID、设备密钥和经过独立核验的 CA。`config.local.h` 已被 Git 忽略，不得发送到聊天或提交 Git。固件使用设备私钥及 Wi-Fi 密码：本地源代码和 Flash 均含敏感信息，非加密设备可能被读取。

真实服务设备迁移和时间证明端点尚未部署，正式页面的设备功能尚未开放；本程序不能连接目前正式生产流程。CA 真实性、轮换、时间窗口所需硬件时钟漂移保证、真实 HTTP 响应、线程栈与看门狗、断电/NVS 高速写入耐久、冻结与断网行为均未在真机验证。串口仅供诊断，无独立可见的容量/故障指示；1 秒实时目标和 2 秒续约在真实网络中未得到保证。候选程序不得投产，也不得清除旧 NVS 以掩盖读取失败。

构建候选：在本地配置完毕后使用 `pio run -d firmware/production`。在隔离测试环境、备份现有固件与数据后方可烧录。切勿在生产设备上直接验证。

当前示例预配置的是**隔离测试项目**的公开地址、publishable key 和测试时验证的 GTS Root R4（SHA-256 指纹见配置文件）；设备 ID、密钥及 Wi-Fi 仍为空。真实设备上线或证书链变化前必须重新检查信任链，不能将此设置视为正式环境的长期证书配置。串口每隔约 1 秒可能显示 `WIFI`、`TIME`、`BOUND` 和 `PENDING`，但该状态不证明可确认或完整同步，串口可能因缓冲区繁忙而跳过输出。

## 实验性：任务进度看门狗（尚未通过实板故障注入）

独立 FreeRTOS 软件监督任务检查计数任务和网络任务的进度；普通 Wi-Fi、
HTTPS 或时间证明失败只要任务仍在重试，就不视为卡死。任一任务连续约
90 秒没有进展、观察到按键释放至少约 1 秒且恢复次数未超限时，才尝试整板
软件重启。采样间隔约 500ms，无法保证捕捉每次短按；检测和重启之间也有
竞争窗口。重启会中断按键采样和可能正在写入的 NVS，极短窗口仍可能漏数、
存储异常或进入故障；确认中途重启可能等待恢复/取消，不能视作已确认。
故障、容量满等故意停止状态不通过重启掩盖。检查同一任务在途执行，不会
自动取消请求；超时不证明服务器没处理。

RTC 内存记录连续自动重启，最多三次；健康进展连续约 10 分钟后重置额度。
达到上限输出 `WATCHDOG: restart limit reached`（串口是尽力输出），停止
自动重启而非无限循环。RTC 记录在断电、掉压及某些重启条件下可能丢失，
不保证跨断电限次。该方案依赖调度器和监督任务继续运行：不能保证发现
整个调度器、CPU 或供电故障，也不能恢复热点或外部服务器，不能保证零
断连。故障注入、NVS 断电恢复、确认中重启、限次和长期板测均必须实测。
不得为解除故障擦除 NVS。它不是独立硬件看门狗，也不代表生产可用。

## 实验性：USB 串口诊断不中断计数

在 ESP32-S3 USB CDC 启动配置下，将串口发送锁等待上限设置为 0，输出前
检查串口就绪并在缓冲区不足时跳过；诊断可能丢失，但不改变计数、冻结或
网络认证。Arduino 核心版本和 USB 连接行为会影响该机制；自动化模拟不能
证明真实硬件重新连接后串口必定恢复，也不能证明空白是串口导致的。若设备
停机、网络故障或 USB 驱动故障，此改动不保证解决。不得为恢复日志擦除 NVS。

## 实验性：提前刷新可信时间

根据实板日志，尝试在有效窗口过半后提前获取新时间证明，而不是每次等待
60 秒失效。新证明失败时旧证明只可用到**原到期时刻**，不延长有效期；
到期或 Wi-Fi 断开仍禁止设备 RPC，持续按原策略重试。仍验证证明、TLS
证书链和主机名。冻结操作已经进入网络处理后暂缓提前刷新，硬到期则仍需
恢复时间；重启或确认请求开始前刷新仍可能延迟确认。每次提前刷新会关闭
复用连接并占用网络任务最长约 4500ms，可能短暂减慢上传。该实验不保证
不断网、不保证确认成功，也不证明已解决一小时故障；需长期实板验证。

## 隔离测试：时间同步诊断

当串口 `WIFI=1 TIME=0` 持续时，固件每隔约 5 秒尽力打印一行
`TIME_DIAG stage=<数字> result=<数字> code=<数字> budget=<毫秒>`。这些数字仅用于定位问题，
不包含 Wi-Fi、设备 ID、密钥、生产单或请求内容。串口 115200，若使用板载
原生 USB CDC，请连接开发板标注 USB 的接口并选择对应端口。输出是尽力而为，
不应将没有看到诊断行视作状态正常。

`stage`：0 尚未开始、1 参数校验、2 随机数、3 DNS/TCP、4 TLS 配置、
5 TLS 握手、6 请求发送、7 响应接收、8 时间证明校验、9 本机时间窗口、
10 完成。`result`：0 成功、1 超时、2 不可用、3 证明无效；`code` 在部分
TLS/HTTP 故障时是错误数字或 HTTP 状态码，其余情况通常为 0。不同阶段的
数字仅是定位线索，不应以此绕过 TLS、改用不安全连接或删除本地数据。

状态输出由每 5 秒调整为约每 1 秒，仅改善串口可观察性，不会加快网络上传。输出仍是尽力而为，串口繁忙时可能跳过。

时间证明预算包括随机数、DNS/TCP、TLS 和请求响应。首次及提前刷新尝试为
4500ms；可信时间已失效且上次尝试超时后，恢复尝试为 11000ms。`budget` 为
最近完成尝试的预算快照，不是实时计时。签名证明的硬上限为 12000ms；较长
往返的完整耗时计入 UTC 不确定范围，证书全链日期仍须覆盖整个范围。旧证明
的 60 秒有效期不变；无法建立可信时间时仍禁止 RPC。较长恢复会占用网络任务，
可能延迟上传或冻结恢复，不保证网络成功，也不能保证 2 秒租约。失败时还可能打印
`TLS_IO start=<毫秒> tx=<字节数> rx=<字节数>`：start 为从初始化开始到进入
TLS 握手的耗时，tx/rx 为本次 TLS 底层发送/接收的累计字节数（包括握手和
可能的应用数据），仅作定位，不含数据内容。两行均是最近完成尝试的快照，
可能由于任务更新或串口繁忙而不同步或缺失。

设备联网时，`RPC_DIAG k=<数字> r=<数字> s=<数字> n=<数字> h=<数字> u=<数字>`
记录最近一次已执行的设备 RPC，数字不含凭据或订单内容：k 是操作类型
（0 尚未执行、1 查询、2 上传、3 冻结、4 冻结状态、5 续约、6 取消），
r 是执行结果（0 成功、1 请求无效、2 传输错误、3 HTTP 错误、4 响应无效），
s 是 HTTP 阶段（0 尚未开始、1 校验、2 连接、3 发送、4 接收、5 完成），
n 是传输结果（0 成功、1 网络错误、2 超时、3 响应过大、4 本地让路），h 为 HTTP 状态码
（未收到时为 0），u 为本次是否尝试复用已有连接（1 是，0 否，不代表成功）。k=0 时其余数值只是默认值；如果请求未能编码，传输数字
可能仍是上一次的快照。不同线程的数字是尽力显示，可能错过或不同步。

针对实板反复出现的状态查询超时，实验性将设备状态查询和计数上传的完整
网络预算调整为 8000ms；取消和确认状态恢复也使用 8000ms，冻结和续约仍是
3000ms，认证时间恢复预算见上文。取消/状态仅以服务端明确返回的终态解除本地冻结，超时不清除数据。
延长预算可能使绑定和同步变慢，不能保证弱网络成功、不能保证
2 秒内续约；租约超时仍禁止确认，TLS 与时间校验保持不变。上传超时不视作
已确认，保留本地计数并按原协议重试；超时也不代表服务器一定未处理。

`FREEZE b=<数字> f=<数字> c=<数字> i=<数字>` 为设备本地快照：b 为最近已处理的
服务端确认状态（0 无、1 请求、2 就绪、3 完成、4 取消、5 过期），f 为本地
是否冻结，c 为冻结快照是否排空且未被后续按键污染，i 为在途操作类型（与
RPC_DIAG 的 k 一致）。`BAR_RPC` 为最近一次已执行的冻结/状态/续约/取消 RPC
快照，格式与 RPC_DIAG 一致；尚未执行则不打印。它们不显示请求或订单内容，
且并非同一时刻的原子快照，不能单独证明是否可以确认。

此候选试验 HTTPS 连接复用，空闲 5 秒后关闭，断网或时间失效时关闭；每次
读写仍检查认证时间窗口及整个已验证证书链的有效期。异常或不完整响应关闭
连接，不在传输层自动重放请求。超时仍不证明服务器未处理。此优化尚未在
实板验证，也不能保证网络延迟或 2 秒租约成功；不得作为生产就绪依据。

修复慢网络下状态轮询持续抢占绑定/上传的问题：成功查询后至少给予一次
处理结果的机会。此修复基于自动化模拟，仍需实板验证；不能保证热点稳定
或 2 秒冻结续约在高延迟网络下成功。

请保留整个项目和 `config.local.h` 的本地私密副本。常规上传应保持 NVS，
但实际分区、板子连接与断电行为尚未验证；不要运行擦除 Flash、擦除 NVS
或格式化命令，也不要假定重新烧录不会丢失计数。此诊断尚未在实板验证。

`FAULT_DIAG planner=<数字> controller=<数字>` 在同步故障时提供来源，0 表示
该部分没有记录故障；例如 planner=9 表示服务器返回 ready/expired，而本地
没有相应冻结日志。数字仅用于定位，不能单独证明此次历史故障的原因。

租约过期仅是服务端 ready 行的派生状态，并非已取消：固件保持本地冻结，
调用设备取消并等待服务器明确返回 cancelled 或 completed 后才解除冻结。
网络失败或重启时保留日志并恢复原请求；实际板卡和热点尚未验证。

此候选在持续计数时允许状态轮询之间最多两次上传，之后仍会轮询，以避免
绑定变化和确认请求被无期限饿死。上传仍使用原来的绝对累计值和幂等协议；
请求延迟、网络断开和服务器处理速度仍影响显示时间，不能保证实时。

串口计数变化时最多约每 200ms 尝试输出 `COUNT t=... total=... p=...`。
t 是开机以来毫秒数，total 是当前本地绑定/epoch 的累计数，不是网页上的待确认数，设备确认后
也不一定归零；p 是本地未确认上传的数量。串口忙时输出会跳过，
不能以日志是否出现判断计数是否已保存或上传。原状态与故障诊断仍保留。

## 串口监视日志 v1（仅隔离测试）

打开 PlatformIO 串口监视器，波特率 115200。计数上传、冻结、状态、续约、
取消以及失败的普通状态查询会产生以下三行，使用 i 配对；成功的普通状态
查询不输出这三行，所以 i 有间隔是正常的。数字是设备本次启动内的诊断信息，
不是订单号、设备 ID、密码、密钥、请求体或服务器恢复凭证。

- `M1 i=... t=... k=... d=... r=... b=...`：i 为启动内命令序号；t 是
  设备处理完此 RPC 的开机毫秒；k 操作类型与 RPC_DIAG 一致；d 是设备侧
  编码、网络往返和解码的总耗时（毫秒），不含队列等待、网页刷新；
  r=0 成功解码、1 编码参数无效、2 传输错误、3 HTTP 错误、4 回复无效、
  5 因无网络或可信时间未发出；b 为已解码的服务端冻结状态，0 无、
  1 requested、2 ready、3 completed、4 cancelled、5 expired。失败时 b=0
  不代表服务端没有处理。
- `M2 i=... h=... s=... n=... u=...`：HTTP 状态、HTTP 阶段、传输结果和
  是否尝试复用，与 RPC_DIAG 的同名字段一致。未发送或编码失败 n=-1。
- `M3 i=... x=...`：请求携带的本地 epoch 绝对累计值，仅上传/冻结/续约有
  意义，不是本次增量、网页数或确认结果。r=0 仅说明设备收到了可解码回复；
  上传是否被本地状态机确认仍需查看 PENDING 和故障状态，是否实际累计须核对
  网页/服务端。

每约 15 秒尽力输出 `MON v=1 t=... lost=...`，t 是开机毫秒，lost 是本次启动中诊断队列满或
格式失败丢弃的事件数；序号可能回绕或重启后重置，毫秒数约 49.7 天回绕。
输出经过固定容量队列并且不等待串口，不改变计数、网络、冻结或确认；
串口未连接、缓冲区不足、监视器开启太晚、重启等都可能缺失记录，lost=0
也不能保证电脑收到了全部日志。请完整复制 COUNT、M1/M2/M3、MON、FREEZE、
RPC_DIAG 和故障行；请勿发送 config.local.h、Wi-Fi 密码或设备密钥。
串口只能测设备端请求耗时，不能独立测网页显示延迟或证明租约现在有效。

### USB Serial/JTAG 恢复候选与复位诊断

针对 Arduino ESP32 2.0.17 的 HWCDC，主循环在 USB 有总线连接且串口未就绪或 TX
空间不足时，每 250ms 最多一次重新触发发送 FIFO/中断，不清空日志缓冲区、不
重启 USB、不触碰计数或 NVS；这只是一种基于驱动实现的恢复候选，尚未证实本次
串口黑屏的根因，必须实际复测关闭/重开监视器、无监视器及满缓冲场景。诊断
本身仍是尽力而为，不能据串口空白判断离线，也不能保证任何主机或 USB 故障。

`WDT_DIAG reset=<数字> attempts=<数字> hold=<0|1>` 约每 15 秒尽力输出，reset
是 ESP-IDF 的本次启动复位原因枚举，attempts 是软件监督重启预算的当前计数；
两者都不能单独证明本次复位由本看门狗发起。此变更不扩大软件看门狗覆盖范围；
调度器停滞、供电或硬件故障未受保护，实板故障注入与长期可靠性仍未验证。

`WDT_DIAG` 增加 `prior=<0|1>`，在独立时隙尽力输出：1 表示本次软件复位前
RTC 中发现有效的监督重启尝试标记。标记紧邻调用软件重启前写入并在启动时
消费；在写入和复位之间仍有极短竞争窗口，因而 1 不能绝对证明复位因果，0
也不能排除标记丢失或断电。标记只供诊断，不参与计数、确认或重启决策；
软件看门狗的重启限制和条件没有改变。此诊断尚未在实板上验证。

### iPhone 热点 Wi-Fi 省电实验（尚未实板验证）

Arduino 2.0.17 的 STA_START 事件会重新应用 Arduino 缓存的省电模式。
本候选先设置 Arduino 的目标模式，之后通过 ESP-IDF 读取和必要时修正；连接后
和每 15 秒在网络任务中重新检查。设置失败不会阻断联网、计数或清理任何数据。
`WIFI_DIAG ps_off=1` 表示最近一次驱动读取为关闭，0 表示读取到其他模式，
-1 表示尚未读取或读取失败。`set=-2` 表示本次启动以来没有尝试 IDF 修正，
0 表示最近一次修正调用成功，-1 表示失败。它们均是上一次操作的快照，不是
实时链路质量、功耗或实际延迟。该模式可能增加功耗和发热；蓝牙共存不适合
直接使用该配置，本固件不使用蓝牙。它不能保证热点、蜂窝网络或服务器不超时。
Arduino 的 setSleep 返回 false 可能只是模式未变，不能据此判断驱动状态。
本次修复尚未实板验证，也不能称为生产就绪。

### 状态查询让路（隔离候选，未实板验证）

仅在至少一次完整、解码有效的状态查询之后，如果新的按键计数在下一次
状态查询执行期间被本地接受，网络任务可以中止该查询的接收并关闭连接，
使计数有机会更早排队上传。服务器可能仍会完成被中止的查询；该查询不更新
计数，丢弃的响应不授予任何确认权限。一次让路后必须有新的成功状态查询
才能再让路，避免持续按键无限饿死绑定/确认查询。上传、冻结、续约、状态
恢复和取消 RPC 不受此中止策略影响，原来的幂等和失败处理保持不变。
`M2 n=4` 是本地让路，不是服务器返回的错误或确认；n=1/2 仍分别是网络错误
和超时。连接建立、上传和可信时间仍可能慢，既不保证低延迟也不保证在线。

### 查询让路的短暂宽限及分阶段诊断（候选，未实板验证）

发现新计数时，状态查询先尝试继续读取约 250ms；如果完整响应及时到达，
就保留经过验证的连接以供下一个请求复用，否则才让路并关闭连接。250ms 是
受限实验参数，不保证加速：它可能让上传多等待约 250ms，或仍需重新握手；
持续按键时，仍须在两次让路间成功完成状态查询。只在网络任务执行，不改变
计数确认、证明期限或上传幂等；已在途的服务器查询可能仍会完成。

每条 M1/M2/M3 事件新增 `M4 i=<票号> cn=<毫秒> tx=<毫秒> fb=<毫秒> rx=<字节>`。
cn 是从请求开始到 DNS/TCP/TLS 验证完成的总耗时（连接失败时为失败耗时，
复用时通常接近 0），tx 是从请求开始至完整请求写入的耗时，fb 是从请求开始
到读到首段 HTTP 明文的耗时，rx 是此次已读到的 HTTP 明文字节数（包含头部，
不包含 TLS 握手数据）。-1 表示没有到达该阶段；本机写入成功不代表对端已
收到，首字节时间也不能单独归责于数据库或蜂窝网络。票号用于和 M1 配对；
串口输出是尽力而为，可能丢失或延迟。禁止打印正文、密钥或网络地址。
